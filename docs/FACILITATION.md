# ailhat Facilitation Product Thesis

## Purpose

Facilitation is a first-class ailhat product layer. It is not a generic LMS, academy, or disconnected course library.

Its job is to help the human operator become progressively more capable at building, directing, and improving an agentic organization by using what ailhat already knows about the operator's real portfolio, workforce, projects, repositories, evidence, and outcomes.

The core architecture is:

**Portfolio Intelligence → Facilitation → Governed Action → New Evidence → Portfolio Intelligence**

The human capability loop inside Facilitation is:

**Learn → Apply → Observe → Improve**

## Product role

Portfolio Intelligence answers:

> What is happening across what I am building?

Facilitation answers:

> What should I understand or improve next so I can operate this system better?

Agent Direct answers:

> How do I turn this evidence-backed decision into a governed handoff?

Agent OS / Workforce answers:

> What governed task, agents, skills, harness, and host should execute accepted work?

ailhat should remain host-agnostic. It should not become the execution harness, workforce registry, or authorization engine.

## What makes Facilitation distinct

The differentiator is not the curriculum. It is the connection between learning and the user's live operating environment.

A generic learning system might say:

> Learn how delegation boundaries work.

Facilitation should eventually be able to say:

> ailhat detected overlapping authority across two agents in your current workforce. Delegation Boundaries is your highest-value next learning priority.

After learning, ailhat should connect the concept back to live portfolio/workforce evidence and observe whether the resulting change improved outcomes.

That creates a closed loop:

**Observe → Detect → Teach → Apply → Measure → Improve → Observe**

## Evidence rule

Facilitation inherits `docs/PORTFOLIO_EVIDENCE_ARCHITECTURE.md`.

- Production evidence describes what users can experience now.
- Repository evidence can ground implementation examples and active-build context but does not prove deployment.
- Deployment evidence can show that a revision shipped but does not prove an original condition is resolved.
- Outcome and verification evidence should be linked back to the originating learning/application context when available.
- Missing telemetry or integrations remain unknown; do not invent personalized guidance from unavailable evidence.
- Preserve source, timestamp, confidence, and epistemic status when a lesson cites portfolio evidence.

## Facilitation experience

The experience should be organized around three states.

### 1. Understand

Teach concepts such as:

- agent architecture and workforce design
- context engineering
- delegation and task decomposition
- tools and skills
- orchestration
- permissions and governance
- evaluation
- human-in-the-loop design
- cost and resource management
- multi-agent coordination
- production reliability

Prefer interactive lessons, simulations, configuration exercises, design challenges, and feedback over passive reading.

### 2. Apply

Connect concepts to the user's actual environment where evidence exists.

Examples include:

- identifying where a learned pattern applies in a live repository
- surfacing overlapping agent responsibilities
- connecting an evaluation lesson to a real weak evaluation boundary
- translating orchestration concepts into a recommended workforce change
- comparing an implementation intention in a repository with what is actually deployed

Do not imply live integration or telemetry when it does not yet exist.

### 3. Improve

Measure whether changes actually produced better outcomes.

Useful signals include:

- tasks attempted and completed
- successful outcomes
- failures and retries
- human intervention
- execution cost and latency
- review burden
- tool/agent utilization
- recurring failure patterns
- quality/evaluation scores
- improvement over time

Avoid vanity metrics based only on raw activity.

## User modes at the point of need

Facilitation should be available where the user encounters a real decision rather than forcing a trip to a separate education surface.

Useful entry points are:

- a finding → **Understand this**
- a recommendation → **Guide me through it**
- an accepted work item → **Learn before delegating**
- workforce-related work → **Build with facilitation**
- completed/external work → **Review what changed**

The user should be able to move between **teach me**, **guide me**, **prepare for delegation**, and **review** without changing products.

A dedicated Facilitation surface can exist for continuity, but it should aggregate learning generated by real portfolio work rather than become a disconnected course catalog.

## Guided build mode

For work the user wants to understand rather than simply hand off, ailhat should provide a step-by-step facilitated path.

Examples include:

- designing an agent workforce
- defining agent responsibilities
- selecting or evaluating skills
- improving handoffs
- creating evaluation criteria
- understanding harness/host tradeoffs
- measuring workforce productivity
- improving product readiness
- validating recommendations before execution

Guidance should always preserve the distinction between learning, decision, authorization, execution, and verification.

## Capability continuity

Facilitation should track more than lesson completion.

Useful continuity state can include:

- concepts introduced
- concepts demonstrated
- confidence reported by the user
- exercises completed
- live applications of the concept
- recurring failure patterns
- interventions that improved outcomes
- areas where the user still needs support

This should produce a living capability profile, not a vanity score.

### Live-project continuity

A lesson should not disappear after completion. When the same pattern appears later, ailhat should be able to reference the prior intervention and ask whether the concept transferred successfully instead of restarting from zero.

Example:

> You previously applied a delegation-boundary change to Product A. A similar overlap now appears in Product B. Here is what changed last time and what still needs verification here.

Continuity must remain evidence-backed: prior exposure to a concept is not proof of mastery.

## Real-time assistance and feedback

During live work, Facilitation may review a plan, prompt, agent design, workflow, handoff, evaluation, or decision and provide feedback tied to the current objective.

Feedback should distinguish:

- factual/evidence problems
- weak reasoning
- missing context
- capability gaps
- execution risk
- authorization constraints
- opportunities to delegate safely

Do not collapse these into one generic quality score.

## Adaptive learning priority

Facilitation should eventually generate learning priorities from live portfolio/workforce evidence.

Example UI concept:

### YOUR NEXT LEARNING PRIORITY

**Delegation Boundaries**

ailhat detected overlapping responsibilities across two agents involved in active work.

**Why this matters to you**

Overlapping authority can increase duplicated work, retries, and human intervention.

`8 min · Intermediate · Based on your workforce`

After completion, the experience should be able to surface:

### PUT THIS INTO PRACTICE

ailhat identified places where this principle may apply to your current workforce.

This is the intended direction: adaptive professional development generated from the condition of the user's real agentic organization.

## Facilitation record

A normalized facilitation record should be able to reference:

- `product_ref`
- `finding_ref`
- `work_item_ref`
- `objective`
- `concept`
- `why_now`
- `evidence_refs`
- `mode` (`teach`, `guide`, `prepare-to-delegate`, `review`)
- `steps`
- `user_confidence`
- `completion_state`
- `capability_signal`
- `outcome_ref`
- `verification_ref`
- `created_at`
- `updated_at`

This can begin as application state; it does not require a new public service boundary.

## Ecosystem boundaries

### ailhat

Owns Portfolio Intelligence, Facilitation, evidence-backed recommendations, lifecycle interpretation, and outcome measurement.

### Agent Direct

Agent Direct is an ailhat-facing interaction for preparing/handing accepted work into governed action. It does not itself grant authority or become the execution runtime.

### Agent OS / Workforce

Agent OS / Workforce is foundational infrastructure and a through-line across the ecosystem, not a separate public product offering. It owns task-first workforce composition, agent identities, skills, routing, handoffs, and host/harness-independent execution policy.

### Agent Control

Agent Control is the authorization-intelligence layer in the Agent OS control plane where integrated. It is not a separate public ailhat offering and should not be described as the generic execution-capacity UI.

### LEDGATo

LEDGATo participates when work materially intersects its defined governance or enforcement scope. Do not route generic authorization or ordinary portfolio work to it by default.

### Agentic harnesses and hosts

cto.new, Codex, CI, local workstations, and other compatible environments are replaceable execution harnesses/hosts. ailhat must remain harness-agnostic.

### ALVIRA / MeOS

Owns Context Intelligence and durable understanding of the person or organization. ailhat should consume only approved, minimum-relevant context when needed.

## Product rule

A feature belongs in Facilitation when it uses ailhat's understanding of the user's real portfolio/workforce to make the operator more capable.

If a feature only teaches generic AI concepts without connecting them to the user's live operating environment, it should not define the Facilitation experience.

## Implementation sequence

### Phase 1 — contextual entry points

- expose **Understand this**, **Guide me through it**, **Learn before delegating**, and **Review what changed** around existing findings/work
- keep functionality advisory; no new execution authority

### Phase 2 — guided interaction

- add contextual micro-lessons grounded in evidence
- add teach / guide / prepare-to-delegate modes
- persist basic lesson and confidence state

### Phase 3 — capability continuity

- connect facilitation records to work items and outcome/verification evidence
- track recurring gaps and demonstrated application
- adapt future guidance based on prior application without assuming mastery

### Phase 4 — workforce facilitation

- add guided workforce-design and evaluation experiences
- measure productivity and handoff quality against portfolio objectives
- recommend Agent OS / harness execution paths when appropriate

## Success criteria

Facilitation is working when a user can move from:

> ailhat found something important

through:

> I understand why it matters and what good looks like

into:

> I can act myself, build the capability, or delegate it intelligently

and ailhat can later determine, from evidence, whether that intervention actually improved the portfolio.
